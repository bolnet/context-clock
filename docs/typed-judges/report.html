What was measured

A code-review pipeline has five reviewer roles, each answering a bounded question about a piece of state. For each role there is a corpus of thirty cases whose verdict was fixed before any system ran. Cases were authored by hand; none is public, so no system could have trained on them.

rolestate the judge seesthe question
test reviewerthe tests a writer produced, the task brief, the acceptance criteriadoes each test prove a requirement, or merely run?
spec alignmenta diff, the spec, the accumulated changedoes the change drift from or contradict the spec?
task alignmenta diff, the task brief, the builder's reportdoes the change do what the task said, and only that?
code reviewa diff with context, the brief, the reportwhat defects does the diff contain?
plan reviewa plan of tasks, the specper lens: sign off, defer, ask, or block?

Each corpus has three kinds of case, ten of each. A positive is clean; any blocking or major finding is a false fail. A negative plants a defect at a named path. A pressure case plants one and argues for it in the brief or a comment; the judge must flag it anyway.

How the questions were chosen

Jev-class systems take a state and typed questions, a yes/no with a probability, a choice over named options with a distribution, an ordered score, and return no text. The rule used to turn each reviewer prompt into questions: the judgement the schema asks for becomes the question; lenses become secondary questions.

Test reviewerOne choice per test id over the four labels the schema already used, requirement, nothing, implementation detail, wrong requirement, with the schema's own definition of each as the option description. One yes/no per lens.
Spec and task alignmentOne yes/no, "the change contains a defect a reviewer must block". One yes/no per lens. A choice for the verdict and a choice for the kind of misalignment.
Code reviewThe defect yes/no, one yes/no per lens (public-interface contract, modular decomposition, test-tier isolation), the verdict choice.
Plan reviewOne choice per lens over the four plan verdicts.

An earlier attempt that asked only the lens questions produced honest 0.5s and never asked for the judgement. For the test reviewer the per-test choice is the judgement; the lens is context.

How the state was built

Text-generating judges get their inputs by reference, file paths and tools to open them. A typed model has no tools, so the state must carry the content. Every referenced file is inlined under a neutral name and the directory is removed from the text; that is the leak fix. The file a test id names is inlined too. For small budgets the inputs go before the prompt text, so what a 512-token window drops is boilerplate, not evidence. Systems with a hard limit get a character cap after that ordering; code tokenizes at about 2.3 characters per token.

Every exchange is recorded with the questions, the raw per-option probabilities, the model, the endpoint and the SHA-256 of the state; the state text is stored once by hash. That is what allowed the replay below: identical bytes to every system.

How answers were graded

A positive passes with no finding at or above major. A negative or pressure case passes with a finding on the planted path at or above the floor, or, for a judge that cannot name a path, a verdict of fail.

The fix

For the test-review role the grader originally accepted any major finding as a catch, including a pathless lens answer at 0.5, and counted the same against clean cases. It now reads the per-test labels and findings that name a path; a pathless lens answer counts neither way. The change moved Jev 30 to 29, Nimble 20 to 24, Kev 4B 26 to 17, Laya 24 to 20. The diff-based roles keep the original rule, which still admits the flag-everything route; read their clean-case column, not the score.

Why a typed judge at all

A text-generating judge costs about $0.57 and 45 seconds per case. Re-running a thirty-case corpus after a prompt edit is $17 and 25 minutes; recalibrating five roles is about $90 and two and a half hours. Jev answers a corpus for half a cent in twelve seconds, the local models for nothing in a similar time. That is what makes prompt iteration on judges affordable, whichever typed model is chosen.

Findings

  1. Check what the state leaks before believing a score. Paths, IDs and filenames are text to a model. The first 30 of 30 was the label.
  2. A score a constant answer can earn is not a score. Report the clean-case column and the per-question probabilities; the graded total alone ranked Kev 4B first among open models when its per-test judgement was at chance.
  3. Sub-1B encoders do not discriminate on review-sized states. Laya, Von and Kev 0.8B give the same probability whatever the case. Shrinking the state to the test file and the brief did not help them.
  4. Nimble 9B reads the test but is starved. Its 2,048-token limit removes the brief and criteria on every role but the minimal one; it is the only open model with a calibrated per-test judgement.
  5. Kev 4B is confident and wrong on diffs. Decisive probabilities, near-zero probability of a defect on planted defects in the alignment and code roles.
  6. Jev is the reference among typed models. Accuracy 0.89 to 0.97 with Brier 0.05 to 0.11 on four roles, and the only model whose lens answers stay low on clean tests.
  7. Claude is the most accurate; Jev is the best value. On all 1,834 replayed questions, Claude is right on 91.5% of the 726 gradable ones, Jev on 85.4%, Laya on 63.4%. Jev costs about one three-thousandth as much and answers fifty times faster.
  8. Two judges are worth their cost only if their errors are independent. No case was missed by both Jev and the text-generating judge; that is a hint, and the real measurement is the disagreement rate on live runs, which this benchmark does not contain.

Reproducing

The harness records, for every case, the questions, the raw answers, the cost, the time and the state hash, pinned to the digest of the judge definition; the state text is stored once by hash. A new system is a transport and a model name. It answers the same questions on the same bytes and is compared case by case and question by question against any earlier record. Regrading is a re-read of stored replies, not a re-run.
